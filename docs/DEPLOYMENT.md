# Deployment preparation

This document describes the existing container boundary and the prerequisites for a later deployment. **No AWS resources have been provisioned, no deployment has been performed, and no container build is considered verified unless recorded by a build run.** PostgreSQL runtime and browser E2E validation remain outstanding.

## Current deployable processes

| Image | Entrypoint | Health behavior |
|---|---|---|
| `Dockerfile.api` | `uvicorn claimcheck.api.app:app --host 0.0.0.0 --port 8000` | Container liveness calls `GET /healthz`; configure platform readiness to call `GET /readyz`. |
| `Dockerfile.worker` | Existing `claimcheck-worker` console entrypoint | Long-running PostgreSQL job consumer; no HTTP health port. Monitor process health and durable job heartbeats/status. |

Both images use `python:3.12-slim-bookworm`, install the declared production package, run as UID/GID `10001`, and take settings from environment variables. The worker image installs the existing Tesseract system binary required by the current OCR path. API and worker use the same `DATABASE_URL` and private storage location. Do not add another queue, cache, or worker architecture.

Build locally after installing Docker:

```bash
docker build -f Dockerfile.api -t claimcheck-api:local .
docker build -f Dockerfile.worker -t claimcheck-worker:local .
```

The API image includes `alembic.ini` and migrations for explicit deployment-time migration execution. It does not apply schema changes at application startup. Deploy a migration job/release step before new API/worker code that depends on the schema; avoid multiple instances independently racing migrations.

## Environment contract

Use only the settings implemented by this repository:

| Variable | Purpose |
|---|---|
| `CLAIMCHECK_ENV` | Explicit `development` enables local fixed identity and dev-only routes; production mode is the safe default. |
| `DATABASE_URL` | PostgreSQL URL, e.g. `postgresql+psycopg://…`; SQLite is rejected. |
| `CLAIMCHECK_STORAGE_ROOT` | Private local-storage root shared by API and worker. |
| `CLAIMCHECK_MAX_UPLOAD_BYTES` | Maximum upload size in bytes. |
| `CLAIMCHECK_MAX_REQUEST_BYTES` | Maximum request body size in bytes; cannot be smaller than the file limit. |
| `CLAIMCHECK_MAX_PDF_PAGES` | Maximum PDF page count. |
| `CLAIMCHECK_OCR_ENABLED` | Existing worker OCR toggle. |
| `CLAIMCHECK_CORS_ORIGINS` | Optional comma-separated exact browser origins; HTTPS only except localhost HTTP in development. |
| `CLAIMCHECK_WORKER_ID` | Optional stable worker label; otherwise generated by the process. |
| `CLAIMCHECK_WORKER_POLL_SECONDS` | Worker queue poll interval. |
| `CLAIMCHECK_WORKER_LEASE_SECONDS` | Durable-job lease length. |
| `CLAIMCHECK_WORKER_HEARTBEAT_SECONDS` | Worker lease heartbeat interval. |
| `CLAIMCHECK_WORKER_RETRY_SECONDS` | Retry delay for retryable jobs. |
| `CLAIMCHECK_LOG_LEVEL` | Python process logging level. |
| `CLAIMCHECK_DEV_OWNER_ID` | Optional fixed development identity only; never production authentication. |

See the safe placeholders and local/test/production examples in [`.env.example`](../.env.example). In production, inject database credentials and identity-provider secrets from a secret manager; do not copy the local Compose password or `.env` file into an image.

## Production readiness gates

These items must be completed and verified before real-user traffic:

1. **Identity / authorization:** integrate the intended server-side identity provider. The repository intentionally has no production OIDC implementation. A production API without an injected provider returns `401` for case resources; do not treat the local development principal as authentication.
2. **PostgreSQL:** provision a supported managed PostgreSQL service, private networking, TLS, backup/restore, monitoring, and a tested migration/rollback plan. Apply the single Alembic head (`b31f5c2a9e70`) using the migration release step. PostgreSQL integration/runtime tests have not been run in Arena.
3. **Private document storage:** today the app uses `PrivateLocalFileStorage`. For one host, a protected persistent volume must be mounted consistently. Horizontally scaled API/worker instances need a shared private storage service/volume. A future private S3-compatible adapter may implement the existing `Storage` port and readiness check, preserving opaque keys, SHA-256 metadata, owner-scoped workflows, integrity verification, and deletion semantics. **No S3 adapter, bucket migration, or object-storage deployment is implemented here.** Do not put uploads in a public bucket or serve a private volume as static content.
4. **Network and browser origin:** terminate HTTPS at the deployment edge, keep PostgreSQL and storage private, and set `CLAIMCHECK_CORS_ORIGINS` only to exact HTTPS frontend origins when cross-origin access is genuinely needed. CORS is not authentication. Same-origin hosting is preferred.
5. **Separate runtime roles:** deploy API and worker as separately scaled processes/images; give them access only to the configured database and private storage. The current processes use `DATABASE_URL`; environment-specific database privilege design still requires operator review.
6. **Operations:** define secret rotation, deletion across backups/replicas, retention, audit/log access, alerting on readiness and stuck/failed jobs, incident response, resource limits, and restore drills. No compliance certification is claimed.
7. **Frontend:** build the static bundle with the checked-in Node/Vite toolchain; host it behind the same origin where practical. Do not bake private values into Vite client variables or browser code.

## Health, rollout, and rollback

- `GET /healthz` is liveness only and can remain successful when the database is unavailable.
- `GET /readyz` verifies PostgreSQL with a lightweight query and checks private storage readiness. Use it as the platform readiness gate before routing traffic.
- Run migrations once as a controlled release step. Verify API readiness, worker liveness/heartbeats, and job status before shifting traffic.
- Keep API and worker on compatible schema/application versions during rollout. A worker should not claim `DOCUMENT_PROCESS` or `DOCUMENT_DELETE` jobs until its DB and shared storage are available.
- Rollback must account for whether a forward migration is reversible and whether any new-format jobs/data were written. Never assume a code rollback reverses database or stored-object changes.

## Arena boundary

This is deployment preparation only. Do not interpret the presence of Dockerfiles, the local Compose PostgreSQL service, unit tests, or Alembic graph validation as proof of a PostgreSQL runtime, AWS deployment, private S3 migration, production identity, browser E2E, or security review. The next required verification is a disposable PostgreSQL-backed API/worker upload-to-analysis path, followed by browser E2E and blocker-only fixes.
